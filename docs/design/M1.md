# M1 — SQLite storage, notebooks, originals, jobs

Roadmap: `docs/roadmap/notebooklm-parity.md`.

## Goal

Replace the single JSON corpus with SQLite. Add notebooks as the unit of
isolation, keep uploaded originals, run ingestion as background jobs that
survive restarts, and keep every `/api/*` v1 route working against a
"Default notebook".

## Data

`app/migrations/NNN_name.sql`, applied in order by `app/core/db.py` and
recorded in `schema_migrations`. M1 creates `users`, `notebooks`,
`memberships`, `sources`, `source_files`, `chunks`, `chunk_vectors`, `jobs` and
a small `app_meta` key/value table. Later milestones add their tables as new
numbered files; a shipped migration is never edited.

- SQLite in WAL mode, `foreign_keys=ON`. Deleting a source cascades to its
  chunks and vectors.
- Vectors are float32 BLOBs (`array('f')`, stdlib), keyed by
  `(chunk_id, embedder_signature)`. When the signature changes, vectors are
  recomputed on load and written back, which is the same contract the JSON
  store had.
- `UNIQUE(notebook_id, sha256)`: duplicate rejection is per notebook. The same
  file may live in two notebooks.
- Each source keeps `DATA_DIR/notebooks/{nb}/sources/{id}/original/<name>` and
  `extracted.txt`. Extracted text is stored now so M2's character anchors have
  a stable reference text.

## Isolation (I1, I2)

`NotebookRegistry` maps `notebook_id -> NotebookStore`. Each `NotebookStore`
owns its own `HybridIndex`, built lazily from that notebook's rows only. There
is no shared index, so IDF, coverage, facets and candidates are per notebook
by construction, not by filtering. Within a notebook, IDF stays global to the
notebook, as before.

`NotebookStore` implements the `DocumentStore` interface (`add`,
`list_documents`, `facets`, `count_matching`, `index`, ...), so `ChatEngine`
and the gate are unchanged.

Only `ready` sources are indexed or counted. A notebook whose sources are all
still queued is `no_corpus` to the gate, which is correct: there is nothing
to answer from yet.

## Jobs

`jobs` table plus an in-process `ThreadPoolExecutor` (`JOB_WORKERS`, default
2). Ingest jobs read the original from disk, so a job is just a pointer and
can be re-run after a crash. On boot, `running` jobs return to `queued`,
`processing` sources return to `queued`, and every queued job is resubmitted.
Cancelling a queued job takes effect immediately; a running job checks the
flag between extract, chunk and index.

v1 `POST /api/documents` stays synchronous, because the legacy contract
returns the ingested documents in the response. v2 `POST .../sources` returns
job ids.

## Legacy import

On first boot, if `DATA_DIR/corpus.json` exists, it is copied to
`DATA_DIR/legacy-backup-<timestamp>/` along with `persona.json`, loaded through
the existing `DocumentStore` (so every corrupt-file and v1/v2 tolerance already
tested applies), and written into the Default notebook. `corpus.json` is then
moved into the backup folder so it cannot be imported twice. Completion is
recorded in `app_meta`. `persona.json` stays where it is, because the v1
persona routes still use it, and a copy goes into the Default notebook's
`chat_config_json` for M4.

## API (`/api/v2`)

Notebooks: list, create, get, patch, delete, copy (sources only; chats, notes
and artifacts don't exist yet). Sources: upload (multipart, or JSON
`{kind:"text"}`), list, get, content, original file, patch, delete. Plus
facets, search (no LLM, no key: I9), jobs get/cancel, and `GET /me`.
`SINGLE_USER_MODE=true` by default: every request acts as the `local` user.

## Risks

- One SQLite connection guarded by a lock. That is fine for a single process.
  Multiple uvicorn workers would each hold an in-memory index that goes stale
  when another worker writes. That is documented, not solved, in M1.
- Pure-Python cosine stays until M3 (NumPy). Per-upload cost no longer grows
  with corpus size, but search over 100k chunks will be slow until then.
